1. 为什么要重构：三个把产品做小的错误

错误一：把一个会过期的政策窗口固化进架构

v3.0 里到处是 scope: "site:TW"，利润公式、门禁、状态机全部绑在「Shopee 台湾 + 无货源直发」上。但台湾之所以能跑通无货源，靠的是低值免税门槛仍在——这是一条会变的政策，不是一条不会变的平台规则。

泰国就是已经发生的反例：1500 铢免税取消后，所有进口商品统一征关税 + 7% VAT，行业报道的原话是「低价铺货模式加速退场」「本地仓从可选项变必选项」。同一个无货源模式，换个市场，经济性直接归零。

结论：如果「台湾」写在代码里，那么泰国政策一变，你要改的是架构；如果市场是参数维度，你要改的是一个 JSON 文件。

错误二：把履约模式当成了产品本身

无货源只是「不持有库存、靠上游代发」这一种履约方式。同一个人在同一家店，明天可能改成备货到海外仓（税负上升时更划算），或者接一个全托管的供货单。这三种模式的差别在履约与资金节奏，不在选品逻辑、成本科目框架、证据纪律。

把它们写成三套系统，会有三套参数表、三套证据标准、三套门禁——然后互相漂移。

错误三：把平台的横向能力私有化

证据分级、参数生命周期、门禁服务、成本核算、审计留痕、KPI 校准——这六件事在任何模式、任何平台、任何市场都一模一样。它们不该属于任何一个模块，更不该属于某一个模式。

2. 一条架构原则

不变的能力上提为平台级，会变的模式下沉为插件。

判断标准很简单，问三句：

问题答案归宿
换平台/换市场/换模式后，这东西还一样吗？一样横向能力（平台级）
它是一个会随政策、平台、季节变化的值吗？是参数（带 scope 与复核日期）
只有某种履约方式才需要它吗？是模式插件（modes/<id>）

5. 市场可行性：无货源不是只限台湾

「无货源只限台湾」这个说法，起点是一条 E 级待核实规则（个体户执照首站可能仅限台湾）。它有三个错位：① 它是 E 级，按本架构自己的纪律不得用于决策；② 它约束的是首店，不是永久站点范围；③ 它管的是入驻，与履约模式无因果关系。

真实情况是：无货源到处都能做，但「中国小包直发 + 低值免税」这个打法正在被逐国关闭。

市场低值免税现状无货源可行性依据
TW门槛仍在（2000 TWD 起征） viable SLS 时效 4-8 天、地理距离最近、免税窗口未关。注意：这是窗口，不是特权——窗口会关
TH已取消（2026-01-01 起 1 铢起征） degraded 关税 + 增值税合计不低于 17%（低值关税 10% 起、VAT 7%）；但税由平台在买家下单时代收（2025-12-22 五平台协议），冲击落在买家端价格与转化，而非卖家毛利。来源：国家税务总局转述泰王国海关署（政府二手）
MYLVG 10% 销售税且强化执行 degraded 500 令吉以下征 10%；50 令吉商品被征 5 令吉，叠加佣金与物流后利润可能归零；2026-10-09 预算案是关键节点
BR20% 关税体系not_viable长时效 + 高税负，直发模型不可行
MX监管收紧not_viable同批公告中与巴西一并调整
三条纪律：
  • dropship_viability 是 advisory，只能提示（R-MKT-001），不得自动停售或拦截。
  • 该字段由参数驱动（免税门槛、VAT、时效），不来自人工判断；参数一变，可行性结论跟着变。
  • 当市场不再是 intact 时，核算模型必须计入关税与进口 VAT，否则会系统性高估利润（R-MKT-002）。
市场结论来源：泰国 ksher 2026-09-16；马来西亚 ksher 2026-09-17。均为行业媒体，故标 E 级 + unverified_claim，并生成 VT-045 / VT-046 待官方原文升级为 A。

M6 是当前最大结构性空白。v3.0 的八道门里七道在讲「别做错」，没有一道在讲「怎么被看见」；KPI 里也没有曝光、访客、加购、转化。对无货源铺货来说，成败主要在曝光——这不是补一个报表的事，是要把一条完整的链路建模出来。

7. 履约模式插件化与边界规则

模式状态模式独占能力（owns）资金/库存特征
dropship
无货源一件代发		已实现 库存前置检查、代发地址格式校验、货代贴单、采购垫付与回款周期、断货降级链路 无库存风险；出单后垫付；对周转金极敏感
stock
备货 / 海外仓		待实现 补货计划、库存周转、批量清关、仓储成本摊销 有库存风险；批量清关摊薄税费；市场政策收紧时的主路径
platform_managed
平台全托管		待实现 供货价、审版图审、备货到国内仓 几乎无运营风险；定价权与利润空间被锁定
边界规则（INV-013 / R-GOV-004，硬门禁）：履约模式不得实现自己的参数注册表、成本模型、证据分级或门禁服务，也不得定义选品（G1）与核算（G3）门禁。模式专属参数（mode_params）只是带 scope.mode 的登记，仍由平台 ParamRegistry 统一校验。
这条规则是在重构过程中自查发现的：最初我把 mode_params 放进模式文件，同时又写了「模式不得拥有参数表」，自相矛盾。现在二者已对齐。

10. 证据分级与门禁（沿用 A–E）

等级含义能否硬拦系统行为
A官方硬规则可以（未过期）硬拦；必须有来源 + 查询日期 + 快照（无快照视为无证据）
B卖家后台实测可以硬拦，绑定平台/市场
C自己实测可以单条记录级硬拦
D经验启发不可以只能 WARN / AUTO_FILL
E待验证不可以只能生成任务或 advisory 提示；未核实数值放 unverified_claim

配套新增两条不变量：

  • INV-012 参数 scope 必须与其所在文件的层级一致——否则市场之间会串用参数。
  • INV-013 履约模式不得越权（见第 7 节）。

完整清单见 governance.json#invariants，共 13 条；validate.py 会检查其中可静态判定的部分。

12. 路线图（按模块重排）

阶段周期模块验收标准
MVP3 周 M1 主体与店铺 + M2 选品与商品 + M5 定价与利润
（横向能力：ParamRegistry / CostEngine / GateService G1–G3）		 任意候选品可算出净利润率与 trace；缺数据返回 INCOMPLETE；E 级参数无法进入硬门禁；INV-001..006 通过
V16 周 M3 供应链 + M4 履约（dropship 插件）+ M8 风控

顺序建议：先做门禁（防止亏钱），再做看板（优化效率）；但 M6 不能无限期推后——没有流量模块，前三个模块只是在保证你「不亏得很惨」，而不是「能赚到钱」。
