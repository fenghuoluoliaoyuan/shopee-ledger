1. 使用说明与证据等级

本手册用于 Shopee 无货源一件代发模式的起步阶段，同时作为智能卖家后台的知识底座与规则来源。所有条目均标注证据等级，费率、政策、周期类内容不写死，以官方当期公示为准。

1.1 双重读法

读者读什么用法
人第 1–12 章正文判断、决策、执行动作。遇到紫色「系统落地」框可略过。
系统spec/manual-core.json + 第 13–20 章读参数、规则、门禁、状态机、告警与 KPI，直接生成配置表与校验服务。
维护者第 12 章 + 第 19 章按第 19 章治理流程采集证据、升级等级、发布新版本。

1.2 证据等级（含系统门禁资格）

等级含义写法与处理方式可否作为系统门禁典型用途
A官方硬规则可写死。必须注明来源页面、查询日期、复核状态可硬拦（需未过期）费率、关税起征点、免佣规则
B卖家后台实测账号下来后，从卖家中心抄真实数值可硬拦（绑定站点/类目）SLS 运费档、保证金、DTS 时效
C自己实测数据称重、采购实付、运费报价等可硬拦（单条记录级）实际重量、下单页实付
D经验启发可参考，不写死，标注「经验值」只能软提示，不得硬拦净利润率阈值、退货率预留
E待验证留空，进入第 12 章证据采集任务。不作为第一单门禁禁止进入计算与门禁，只能生成任务首站限制、店配重量、罚分细则

1.3 核实渠道优先级与通道可达性

核实渠道优先级：官方文档 > 卖家中心 > 收款商官网 > 物流商报价 > 自己实测 > 行业经验 > 智能体方案。

shopee.cn/edu 卖家学习中心仅人工机器抓取返回 JS 空壳（"Seller Education Hub"），正文不可机读。必须人工登录截图存档
help.shopee.tw 帮助中心本次不可达2026-10-03 复核 fetch 失败。需在可访问网络环境下人工复核并留存快照
Shopee 卖家中心（登录后）账号下来后可达B 级来源的主要入口，所有费率/时效以这里为准
招商经理 / 官方公告可达E 级冲突项（如首站限制）优先走这条通道书面确认
收款商官网可达提现费率以注册时页面为准
行业媒体（智象出海等）可达可对官方公告做交叉验证：印证公告存在性与细节一致性。不能替代官方原文，只降低「编造」风险，不改变证据等级归属
自己实测最可靠称重、实付、时效，优先于任何二手来源
可达性带来的治理要求（新增）：A 级条目虽然标了来源 URL 与查询日期，但当前无法机器复核。因此：
  • 每条 A 级参数必须记录 复核状态（可机读 / 仅人工 / 阻塞）与 下次复核日期。
  • 到期未复核的 A 级参数自动退出硬门禁，降级为软提示（见第 15 章 R-GOV-002）。
  • 禁止把 A 级参数的价值建立在「某篇文章里写过」上；必须留原始页面快照或登录复核记录。

1.4 三条底线

  • 费率不写死，单独做参数表，每季度更新。
  • 经验值单独标 D，不与官方规则混写。
  • 涉及平台风控红线的操作（去水印、改 MD5、批量差异化、自动抢活动）不写入手册，也不在后台中实现。

1.5 系统门禁五原则（新增）

#原则含义
1只有 A/B/C 能硬拦D 级只能生成提示或默认值，E 级只能生成任务
2缺数据 ≠ 不可做结果状态为 INCOMPLETE，不是 REJECT；提示补哪一项数据
3一切门禁必须可解释拦截时必须给出：规则 ID、依据参数、证据等级、下一步动作
4一切参数必须可追溯来源 URL + 查询日期 + 复核状态 + 复核人
5一切估算必须可校准估算值出单后被实测值替换，并回写阈值（第 18 章）
→ 系统落地（第 13 / 15 / 19 章）
  • 证据等级是一等字段：params[].evidence_level，门禁服务据此决定 hard / soft / advisory。
  • 门禁判定必须返回四元组：{rule_id, result, evidence_level, next_action}。
  • 结果枚举固定为：PASS / INCOMPLETE / WARN / REJECT，禁止只返回布尔值。

2.4 收款账户

  • 候选：连连支付 / Payoneer / PingPong，选其一。
  • 材料：身份证、执照（可后补）、店铺链接（可后补）。
  • 周期：常比店铺审核慢，应最先提交。D
  • 费率参考：台湾站提现费率区间约 0.5%-1.2%（D，无打开的费率页）；连连约 0.7%-0.8%（D，注册页抄到后再替换）、PingPong 约 1%、Payoneer 约 1.2%；另有汇兑损失约 0.3%-0.5%。利润表里取区间上沿预留，再加汇损。以注册时页面为准。
执行顺序：
  1. 执照与收款账户并行提交。
  2. 审核期间：选候选品 → 买样品 → 称重 → 记录 1688 下单页实付 → 询国内运费。先买样品，否则没有重量可录。
  3. 佣金 14% 和手续费 2.5% 现在就填进利润表（免佣窗口内佣金记 0）；账号下来后补 SLS 运费档和当单实际值。

3.3 供应商侧筛选 D

  • 至少能找到 3 家支持一件代发的备选供应商（规则 R-SUP-001）。
  • 主供应商：开店 ≥ 3 年、近 90 天有交易记录（规则 R-SUP-002）。
  • 下单页实付金额（含起批量、优惠券），不录页面标价。

3.4 买家端人工验证（每天 15 分钟）D

在 Shopee 目标站点 APP 搜目标关键词，观察前 20 个结果：

  • 若 3 个以上同款打 5 折以下 → 价格战激烈，新卖家无入场空间，跳过。
  • 若前排评价数普遍 > 500 → 山头已被占住，新链接难进搜索前排，跳过。
  • 若前排多为高运费或低销量链接 → 位置还空着，可作为候选。

5. 利润核算模型（主模型：台湾站 NT$）

站点主次：本章以台湾站（NT$）为主模型，因为个体户执照首站可能只选台湾站，这是读者最可能的路径。马来西亚站（RM）为扩展分支，办了企业执照后才需要。两站参数不通用，各建各的表。

5.1 核心公式

净利润 = 售价 − 采购价(折当地币) − 国内段运费(折当地币) − 净运费成本 − 平台费 − 联盟佣金 − 广告费 − 提现费 − 汇损 − 退货损耗预留

净利润率 = 净利润 ÷ 售价

售价只录商品价，买家运费不进售价。

六项容易算错的地方：
  • 售价只录商品价。买家实付的运费单独进「买家实付运费」字段，不并进售价。
  • 佣金基数 ≠ 售价。佣金按 （商品售价 + 平台商品补贴 − 卖家优惠折扣）× 费率 计算，不含订单运费。是否处于免佣窗口，按第 2.3 节的 19 日规则判断；窗口内佣金记 0。普通单不加预售服务费；只有预售单才另加 3%（含税）。
  • 净运费成本 ≠ SLS 全额。买家已付运费时，只扣「实际 SLS 运费高出买家实付的部分」，即 max(SLS − 买家实付运费, 0)；卖家包邮时才扣全额 SLS。
  • 免运活动费不单列。台湾站免运服务已并入平台基础服务，免运活动费取消。当单页面若又出现这一行，再判断归属，不和 14% 佣金重复扣。
  • 平台费 = 佣金 + 交易手续费，两笔都要含。佣金 14%（含税），交易手续费 2.5%（含税）。免佣窗口内佣金记 0，手续费仍记 2.5%。交易手续费计算基数原文没写，上架前估算时注明「基数未核实，暂按商品价」；出单后改用账单上的交易手续费金额。
  • 退货损耗按「退货率 ×（采购价 + 国内段运费）」预留。跨境货通常退不回国内，按采购侧成本计提，比按售价百分比更贴近实际损失。

5.6 计算引擎规格（新增）

输入: candidate_id, site, fx_rate, params[site], ad_spend_optional
输出: { net_profit, net_margin, status, missing_fields[], trace[] }

1. 校验必填: weight_g, purchase_price_cny, domestic_ship_cny, price_local
     任一缺失 → status=INCOMPLETE, return (missing_fields)
2. 校验三态: 每个数值字段取 null / 0 / value
     null  = 未填 → 计入 missing_fields
     0     = 明确为 0（如未开广告、包邮）
     N/A   = 不适用（如普通单的预售费）→ 按 0 参与计算，但 trace 标注 N/A
3. sls_freight 缺失 → status=INCOMPLETE（唯一允许卡住上架的费率项）
4. 计算:
     purchase_local   = purchase_price_cny * fx_rate
     domestic_local   = domestic_ship_cny  * fx_rate
     net_freight      = max(sls_freight - buyer_paid_freight, 0)
     commission       = in_free_window ? 0 : (price_local + platform_subsidy - seller_discount) * 0.14
     txn_fee          = (price_local + platform_subsidy - seller_discount) * 0.025   // 基数未核实
     presale_fee      = is_presale ? price_local * 0.03 : 0
     platform_fee     = commission + txn_fee + presale_fee
     affiliate        = price_local * affiliate_rate
     withdraw         = price_local * withdraw_rate          // D 级，取区间上沿
     fx_loss          = price_local * fx_loss_rate
     return_reserve   = return_rate * (purchase_local + domestic_local)
     net_profit = price_local - purchase_local - domestic_local - net_freight
                  - platform_fee - affiliate - ad_spend - withdraw - fx_loss - return_reserve
     net_margin = net_profit / price_local
5. 判定:
     net_margin >= 0.15 → PASS
     0.10 <= net_margin < 0.15 → WARN
     net_margin < 0.10 → REJECT
6. 生成 trace: 每个中间量的值、来源、证据等级、参数 ID
7. 出单后: 用当单实测值覆盖估算值，生成 CostSnapshot(new)，保留旧快照用于对比
计算顺序与取整约定：全部用高精度小数计算，只在展示层取整（TWD 取 2 位，比率取 4 位），避免中间取整导致利润虚高。汇率只允许一个来源（参数 P-TW-FX），禁止公式内硬编码。

5.7 三态语义（新增，防止「缺数据」被算成 0）

状态含义系统行为典型场景
null未填/未知进入 missing_fields，结果 INCOMPLETE尚未称重、SLS 运费档未拿到
0明确为零正常参与计算，trace 标「确认为 0」未开广告、卖家包邮
N/A不适用按 0 参与计算，trace 标 N/A普通单的预售服务费
这是本版最重要的工程约束：把未填的提现费当 0 会系统性高估利润。因此提现费率不允许留空，必须按 D 级区间上沿预留；而真正允许留空并卡住上架的，只有 SLS 运费档。

5.8 未核实数值放哪里：unverified_claim（新增）

有些参数确实「有来源说」一个数字（店配 10kg/5kg、液体 100ml、包裹上限 20000 TWD、配送 4-8 天），但这些数字没核实。它们既不能当事实用，也不该被丢掉——丢了就等于每次都要重新检索。

字段含义系统行为
value已核实的可用值E 级必须为 null；硬门禁只认这个字段
unverified_claim未核实的候选值（含来源）只有显式声明 reads_unverified_claim: true 的规则能读，且该规则必须是 advisory_only
intended_level拿到实测后应升到几级升级时写入 value 并清空对 unverified_claim 的依赖
为什么必须分开：如果未核实的 10kg 直接写进 value，某天有人写了个「超重就拦」的硬规则，你的货就会被一个没人验证过的数字拦下来。拆成两个字段后，硬门禁在物理上读不到未核实数据——这是不变量 INV-011（读取 unverified_claim 的规则必须 advisory_only=true、不得为硬门禁、只能输出 WARN 或 INCOMPLETE）。

7.3 履约链路（关键，顺序不能反）

出单后的正确顺序：先查库存 → 确认地址格式 → 安排发货 → 抄当单地址 → 拍单。

  2. 确认供应商接受中转仓地址格式。若 4.1 建档时已确认过，此步跳过。
  3. 确认有货后，回 Shopee 卖家中心对这一单安排发货。
  4. 抄当单页面给出的中转仓地址和收件人格式。地址以当单页面为准，不能用网上抄来的通用仓地址。
  5. 跳转 1688 拍单，收货地址填当单页面给出的中转仓地址，收件人处带 Shopee 订单号。
  6. 供应商发货至中转仓，由 SLS 链路完成后续跨境配送。

填买家海外地址或用网上抄的通用仓地址：货直接出国或中转仓无法分拣，时效与扣分都算在卖家头上。

11.5 现金流预测模型（新增）

可用周转金 = 投入本金 − 已占用（采购在途 + 已发货未回款 + 首批备货）
未来N天采购需求 = Σ(在途订单待采购额) + Σ(预测出单量 × 单均采购成本)

预测出单量 = 过去7天日均出单量 × 趋势系数(默认1.0，D级)

规则:
  R-FIN-001  可用周转金 < 未来7天采购需求          → ALERT（P1）
  R-FIN-002  订单完成超过 25 天仍未到账            → ALERT（P2，阈值 D 级）
  R-FIN-003  在途采购额 > 投入本金 60%             → WARN（避免全押）
  R-FIN-004  预计出单量增长但周转金未增加           → WARN（提示控速）
→ 系统落地
  • 实体 CashLedger：每笔资金进出（投入、采购、运费、广告、回款、提现），现金流预测基于流水而非账面推算。
  • 回款天数用实测校准（订单完成 → 到账的实际天数中位数），跑通后把 D 级 15-25 天替换为实测值并升级为 C。
本章 A 级条目来源：无。打款周期、收款规则均为 E 级待核实；回款周期和提现费率为 D 级经验值 · 查询日期 2026-10-03

13.1 设计目标与验收口径

目标含义可验收的表现
单一事实来源费率、时效、限额、阈值只有一处定义，业务代码不硬编码改一个参数值，全系统生效；能查出这个参数被哪些规则引用
门禁可执行手册里的判断条件变成可运行的规则，人工操作无法绕过未确认库存无法点发货；未称重无法进入核算
闭环可校准估算值被实测值替换，阈值随真实数据更新每个参数有「估算 → 实测」的替换记录与历史版本

  • 规则用声明式条件（字段/运算符/阈值）而非代码，便于运营在受控范围内维护。

16. 状态机规格

16.1 商品生命周轴

candidate(候选)
  └─(R-SEL 通过)─► accepted(已采纳)
        └─(样品到手 & 称重)─► measured(已实测)
              └─(核算完成)─► costed(已核算)
                    ├─ PASS ──────► listed(已上架) ──► 出单
                    ├─ WARN ──────► observe(观察) ──► 补选/调价 ──► costed
                    ├─ REJECT ────► dropped(砍掉)
                    └─ INCOMPLETE ► measured(补数据)
任意状态 ──(命中一票否决)──► rejected(否决，不可回退)

16.2 订单履约状态机（强制顺序）

created(已下单)
  └─► stock_checked(库存已确认)          [前置: 供应商确认有货]
        └─► ship_arranged(已安排发货)     [前置: stock_checked]
              └─► address_captured(地址已抄录)[前置: ship_arranged, 来源=当单页面]
                    └─► po_created(采购单已提交)[前置: address_captured]
                          └─► supplier_shipped(供应商已发货)
                                └─► warehouse_scanned(到仓已扫描)
                                      └─► in_transit(跨境运输中)
                                            └─► delivered(已签收)
                                                  └─► completed(订单完成)
                                                        └─► payable(进入待打款)
                                                              └─► paid(已到账)

异常分支:
  stock_check → all_out  ──► listing_paused(商品下架) + 订单取消流程
  ship_arranged 后 24h 未 po_created ──► 告警 P1
  warehouse_scanned 超期 ──► 迟发风险告警（DTS 参数为 A/B 时启用）

16.3 核实任务状态机

todo ──► doing ──► done(结论已记录) ──► upgraded(参数已升级并发布)
  ▲                    │
  └────────────────────┘ 结论与来源不完整则退回

16.4 参数生命周期

draft(拟定) ──► to_verify(E 级，不可用于门禁) ──► active(可用于门禁)
                                                      │
                                        (超期未复核) ──┴──► stale(自动退出硬门禁)
                                                              │
                                                    复核完成 ──┘─► active
状态机是「闭环」的载体：没有状态机，手册只是建议；有了状态机，流程才可能被系统守住。所有状态变更写 AuditLog，并记录触发规则。

17.2 告警优先级与 SLA

级别场景响应时效通知方式
P0可能造成直接损失或封店：地址来源非法、发货前未确认库存立即（系统硬拦）界面阻断 + 记录
P1影响履约或现金流：发货超时风险、周转金不足、断货当天处理站内待办 + 置顶
P2影响体验或账目：回款超期、订单异常2 个工作日内站内提醒
P3优化类：参数待复核、KPI 待校准按复核周期周报汇总
告警设计原则：宁可少而准，不可多而废。E 级参数一律不产生时效类告警（避免用未核实规则吓唬用户），只产生「待核实」任务。这是本手册「不写死费率」原则在告警层的延伸。

18. 复盘与 KPI 闭环（含参数校准）

18.1 核心 KPI

指标定义校准目标
选品存活率净利润率 ≥15% 的候选数 ÷ 完成核算的候选数校准选品方向，阈值 P-KPI-SURVIVAL-TH
第一单周期激活日期 → 首单出单日期衡量启动效率
采购到仓时长采购单提交 → 到仓扫描（中位数）校准发货截止预警提前量
迟发率迟发订单数 ÷ 发货订单数校准 DTS 参数与供应商评分
退款/退货率退款订单数 ÷ 完成订单数替换 D 级退货率预留 3%-5%
回款天数订单完成 → 到账（中位数）替换 D 级 15-25 天
估算 vs 实测利润偏差(估算净利润率 − 实测净利润率) 的分布校准提现费、汇损、运费估算
单位经济单均净利润、单均采购、单均运费判断是否具备放量条件
断货率断货事件数 ÷ 出单 SKU 数校准供应商备选数量

18.2 校准机制（闭环的关键一环）

估算值实测来源替换时机替换后的影响
SLS 运费（分档估算）当单页面实际运费每单出单后更新该重量档位的实际值，修正后续核算
提现费率（D 级上沿）收款商实际扣费首次提现后参数升级为 C，核算更准
退货率（D 级 3%-5%）真实退款/退货记录累计 ≥20 单后参数升级为 C，按类目细化
回款天数（D 级 15-25 天）实际到账时间累计 ≥5 笔后参数升级为 C，现金流预测更准
采购到仓时长（估）采购单时间戳累计 ≥10 单后提前量自动调整，减少迟发
平台费（按商品价估算基数）平台账单实际金额首单账单后交易手续费基数问题被真实数据消解

18.3 复盘节奏

周期看什么产出
每单估算 vs 实测差异校准任务（若偏差超阈值）
每周迟发率、断货、告警清单供应商评分更新、下架/换供应商决定
每月存活率、单位经济、现金流类目方向调整、预算决策
每季度费率参数复核、E 级任务清账参数版本发布（第 19 章）
闭环的判据（自检）：系统里任意一个数字，都能回答三个问题——它从哪来（来源与证据等级）、谁在用它（被哪些规则引用）、它准不准（是否已被实测校准）。三个问题都答得上，闭环成立。

19.1 参数条目必备字段

字段必填说明

19.2 证据升级路径

升级条件动作
E → B/C卖家中心抄录或自己实测填写 value、来源、日期；to_verify → active；关联核实任务置 upgraded
D → C累计足够实测样本（见 18.2）用实测值替换经验值，并保留旧值到历史
A/B → stale超过 next_review_at 未复核自动退出硬门禁，生成复核任务，UI 标注「已过期」
任何 → 降级来源失效、政策变更、发现冲突立即降级并记录原因，禁止静默保留旧值

19.3 版本与发布

  • 手册与参数表同版本发布：手册 vX.Y 对应参数集 params-vX.Y。
  • 每次发布写入第 21 章变更记录：改了哪些参数、依据什么证据、影响哪些规则。
  • 参数变更不回溯历史订单：旧订单使用旧参数快照，避免账目漂移。
  • 发布前自检：R-GOV-001（无 E 级参数进硬门禁）、R-GOV-003（无跨站混用）必须通过，否则拒绝发布。

交叉验证的效力边界（必须写清楚）：
